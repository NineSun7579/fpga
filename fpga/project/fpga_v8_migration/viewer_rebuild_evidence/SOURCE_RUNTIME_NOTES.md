# Source-grounded buffer, HDMI, model, and test notes

References below are to the immutable recovered `../viewer_build_recovered/inputs` files. The independent executable now reproduces their frozen binary exactly.

`main.cpp:300` opens `/dev/pango_pci_driver` and requests **4 MiB TX and 4 MiB RX**, not a 16 MiB RX allocation. MAP ioctl uses `cmd=0` for TX and `cmd=1` for RX with `total_length=4*1024*1024`; the mmap lengths are each 4 MiB. TX mmap offset is 0; RX selector offset is 1 MiB (`main.cpp:309`–325). That mmap selector is distinct from the `DmaOp.offset_addr` offsets within RX. The read-only live process maps show two `0x400000`-byte driver mappings; `/proc/maps` alone does not identify their allocation ownership or prove driver buffer exclusivity. No code in this viewer grows the Pango RX allocation to 16 MiB. `DmaBuffer::ensure` at `main.cpp:142` grows a separate `/dev/dma_heap/system` RGA buffer and is unrelated to the Pango RX allocation.

`camera_dma.h:8`–16 defines 614,400-byte RGB565 frames (`0x96000`), `0x97000` slot stride, 4 MiB allocation, and scratch start `0x3ff000`. A 16-byte trailer containing the commit tag follows each frame. Slot offsets are relative to RX:

|---|---|---|---|---|---|
| C1 | `0x000000` | `0x096000` | `0x096010` | `0x00800000` | `0x00a00000` |
| C2 | `0x097000` | `0x12d000` | `0x12d010` | `0x00c00000` | `0x00e00000` |
| C3 | `0x12e000` | `0x1c4000` | `0x1c4010` | `0x01000000` | `0x01200000` |
| C4 | `0x1c5000` | `0x25b000` | `0x25b010` | `0x01400000` | `0x01600000` |
| C5 | `0x25c000` | `0x2f2000` | `0x2f2010` | `0x01800000` | `0x01a00000` |

| Shared metadata scratch | `0x3ff000` | — | 16-byte reads end at `0x3ff010` | — | — |

FPGA frame tags live at the selected ping/pong base plus `0x96000` (`main.cpp:74`–80, 398–405). `regRead`, camera tag probes, and chunked `ddrRead` use RX scratch; `regWrite` stages a four-byte value at TX offset 0 but submits a 16-byte transfer (`main.cpp:336`–430). These are the program's address requests, not independent evidence of the current FPGA's mapping.

`cameraRead` holds the per-`PangoDev` DMA mutex while reading tags, selecting the newer ping/pong bank, submitting one `FRAME_BYTES+16` DMA into that camera's RX slot, and checking the copied trailer. It releases the mutex before `copyCameraPixels` moves frame bytes into the worker's owned `QByteArray`. One worker per camera, disjoint camera slots, a separate scratch range, and owned output storage permit that copy to proceed while a different camera issues DMA. The AArch64 copy uses four 128-bit loads/stores per 64-byte iteration and a memcpy tail (`camera_dma.h:28`–47). This mutex and ownership scheme apply within this process. External helper/process exclusion, kernel global MAP behavior, and current allocation ownership remain **not established**. Do not infer safety for a second driver client from this build or from successful CPU copies.

`--prefer-hdmifull` is parsed in `main.cpp:4041`–4052. With no value, or with a following `--...` argument, its value is `on`; otherwise the immediate following token must be exactly lowercase `on`, `off`, or `auto`, with any other value rejected. Default is `auto`. `on` chooses HDMI full view only while all six panes are selected. `auto` waits for an explicit F-key choice; it does not detect HDMI from frame freshness or a receiver signal. `off` initializes the ordinary six-pane mode but F can still override it. `CameraThread::updateHdmiActive` uses the manual override when present, otherwise only preference value 1 (`main.cpp:999`–1003); F toggles that override (`main.cpp:3388`–3396).

HDMI full mode uses physical C5/C6 (zero-based 4/5), suspends C1–C4 workers, and uses a **virtual** inference camera ID 6 which is never a DMA slot. Physical C5/C6 still use their existing six-slot RX map. Their two 640×480 RGB565 halves join into 1280×480, then scale to 640×360 with 60 gray rows above and below in a 640×480 analytics image. The normal model letterbox adds another 80 rows per side, producing content pad 140 in 640×640 (`hdmi_view.h`, `main.cpp:568`, 898–917, 1598–1607). Pair readiness requires both captures within 100 ms, capture skew at most 40 ms, and matching source generations; it does not prove identical transport tags. Refresh/freshness cannot establish whether the incoming optical source was HDMI or cameras (`hdmi_view.h:7`–23).

`--model VALUE` selects the first scanned model whose absolute path contains VALUE, case insensitively (`main.cpp:4171`–4179). It is not a general file loader: models come from the fixed directories in `scanModels` (`main.cpp:191`–268). `--model-index` chooses that scan index; rotation requires 2–4 unique selector matches. Filename keys determine lane/detection family and classes: `seg-linknet-lane640-` gives 2 or 9 lane classes; `tt100k` gives 29; det/seg `yolo11n` gives 4/6; `-3cls-wb` gives zebra/vehicle/person; `yolov8n` with zebra gives 3, otherwise 1 vehicle. The default detection metadata is vehicle. These inferred labels are not schema validation for a new model. The current runtime path uses 640×640 RGB NHWC UINT8 by default, `rknn_run`, floating requested outputs, attribute queries, decoder/NMS, and output release (`main.cpp:1568`–1656). The parent should integrate V8 in another isolated candidate directory, preserving this baseline evidence.
