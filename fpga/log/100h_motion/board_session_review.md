# Board-session static review

Recommendation: fix/preflight the session helper before quiescing the live board. Parent PnR must finish and the programmer's offline evidence checks must pass before scheduling board downtime. This review performed no SSH, hardware, vendor-tool, or script execution; only local reads and this report write. No source or private host tools were changed.

Reviewed `project/tools/motion_board_session.py` (106 lines), `board_host.py`, and the previous `start_camview_display.py`. Also read the saved launch/build receipts, motion viewer locking/scratch implementation, and `program_100h_motion.py` to assess adjacent safeguards. References below are file:line references to those snapshots.

## Findings requiring fixes before quiesce

1. **Ownership checks fail open on command/device failures.** `motion_board_session.py:45-46` discards stderr and uses `fuser ... || true`; missing `fuser`, a missing device, and a real scan failure all become an empty owner list. The same issue exists with `pgrep ... || true` at line 59. This can falsely authorize unload/remove/reconnect or permit a duplicate launch. Require the commands to exist, check expected device state for the action, distinguish documented no-match results from tool errors, and retain diagnostic stderr. Recheck immediately before mutation. A session lock serializes cooperating helpers; it does not prevent unrelated processes opening the device, so ownership must still be verified and unload must remain non-forced.

2. **Running candidate is overwritten before stop.** Lines 80-84 hash the private source and `cp` it onto `<remote_directory>/camview`; `stop_viewer()` is only called at line 89. On a second `start`, that destination can be the running executable: Linux normally rejects opening it for overwrite with `ETXTBSY`, so the restart fails before graceful shutdown. Prefer staging to a unique temporary file, checking the staged SHA256 and executable mode, then stopping the verified viewer and atomically renaming the staged file to `camview`. Hash the actual launch file too; the current hash-before-copy sequence does not bind the launch file to the receipt if the source changes between those operations. Check that the destination is a regular file in the intended private directory, not a symlink.

3. **Quiesce is independent of successful candidate/programming preflight.** Lines 62-66 can take down the baseline with no check of candidate receipts, launch prerequisites, completed PnR/timing evidence, or a validated SRAM plan. Missing/invalid local JSON is discovered only later by `start`, and SSH is opened before any local receipt validation. Validate the local schema/paths/environment and completed build/programmer evidence first; prepare a verified baseline restore plan and verify the remote candidate, log directory, and baseline executable before stopping the viewer. Parent should run the programmer's `--check` only after build completion and inspect its `validated_only` receipt. Do not run hardware programming while parent PnR is active.

4. **Reconnect proves too little about the endpoint.** Lines 70-74 rescan globally, sleep fixed intervals, optionally load a module, then accept any driver symlink on the fixed BDF plus any character node at the expected path. A wrong driver, stale node, or wrong endpoint can pass. Poll to a deadline for the exact BDF, expected vendor/device identity, expected driver/module binding, and matching device-node identity. Record those results. Keep inspection to sysfs/metadata until readiness is established; avoid adding a competing DMA probe while a viewer owns the device. Global rescan is broader than this endpoint; scope it to the appropriate bus if supported/established for this host.

5. **Process/window identity is insufficient.** Lines 50-52 accept every device owner whose `comm` equals `camview`, then the Xlib code at lines 20-24 sends q to the first window with the matching title. A different executable or multiple matching windows can therefore be targeted incorrectly. Require one recognized viewer owner, inspect `/proc/<pid>/exe` against the saved baseline or hash-verified candidate, and match the X window's PID to that owner (reject ambiguous/missing association). Retain graceful q and verify both original process exit and no remaining device owners before unload. Do not add broad `pkill`/`killall` or forced module unload.

6. **No operation-level lock; startup failure leaves an uncertain state.** All actions are independent and there is no lock across check/stop/unload/remove/rescan/start. Two sessions can both pass the empty-owner test and launch simultaneously. Use a shared host-side advisory lock for the entire critical operation, including a bounded launch handshake; avoid a background viewer inheriting that lock indefinitely. Save a state/launch receipt, including the owned PID and command, before reporting success. On failed launch validation, retain logs and report whether that candidate is still running. Any cleanup should target only the process positively identified as created by that operation.

## Launch/SSH stdout: precise assessment

`motion_board_session.py:93-94` currently builds:

```sh
nohup sh -c '<cd && env ... /absolute/camview>' >> '<runtime.log>' 2>&1 </dev/null &
```

The viewer-side stdin, stdout, and stderr are already redirected. Therefore there is **no demonstrated ordinary inherited-SSH-stdout bug in this exact command**. The previous working helper has the same outer background/redirection pattern (`start_camview_display.py:50-56`) and uses `exec ./camview` inside the shell. Do not claim `nohup` necessarily hangs this SSH command: nohup handles SIGHUP; it does not itself guarantee detachment or fd closure, but these explicit redirects address the usual channel-EOF problem.

The new inner command omits `exec`, allowing an extra long-lived shell on shells that do not optimize their final command. Add `exec env ... /absolute/camview` after `cd` to make the launch PID/exit semantics deterministic. If fd/EOF hangs have been observed on this host, inspect sudo's monitor/PTY and descendant fd behavior; deployment policy is not known from these local files. A full detach approach must redirect all three descriptors and close inherited unrelated descriptors; `setsid` alone is not that guarantee. Neither the old pattern nor static inspection proves this host's sudo behavior.

Actual runner weakness: `run()` at lines 36-43 reads stdout to EOF, then stderr, and only afterwards reads exit status. Enough stderr can fill the SSH channel window and block stdout completion; a child retaining a channel fd can also prevent EOF. The 30-second Paramiko channel timeout bounds an individual blocking read, not a clean total operation deadline or cancellation of the remote process. Drain both streams concurrently with a total deadline, close/half-close stdin after supplying sudo input, and preserve command/error context. A timeout can occur after launch has succeeded; do not blindly retry launch and create another viewer.

Background shell status is also not a launch receipt: logfile redirection, cd, env, or exec can fail after the parent background command returns success. Current three-second pgrep/fuser validation catches many failures, but cannot establish that the process is the one just launched, or that a matching X window/rendering pipeline is ready. Capture a deterministic launch PID (with inner exec), validate its executable/hash and ownership, and poll for the associated viewer window with a deadline. Preserve full logs on failure. `>>` mixes restarts in one runtime log; record a launch marker/time or use a per-launch log.

## Process names: 15-character limit is not a current default-path bug

Linux `/proc/<pid>/comm` and default `pgrep` name matching are limited to 15 visible characters. Direct execution of `camview_motion_private` would normally appear as `camview_motion_`, so both `comm == "camview"` and `pgrep -x camview` would miss/reject it. The current saved receipt points to that private build name, but lines 83-84 intentionally copy it to `.../camview`, and line 92 executes that copy. The saved baseline executable also ends in `/camview`. These default paths correctly yield `camview`; do not diagnose truncation as the cause here.

The defect is dependence on a generic, mutable comm value rather than executable identity and an owned launch PID. Keep the alias if desired, but validate `/proc/<pid>/exe`. A custom baseline executable name, an independently launched private-name binary, or a process renaming itself still needs explicit handling; switching indiscriminately to `pgrep -f` introduces command-line false matches.

## Motion polling, DMA locks, and scratch safeguards

The private viewer uses one `PangoDev::dmaMutex_` across complete motion snapshots (`motion_100h/host/camview/main.cpp:153-189`), frame poll/select/transfer (`197-219`), and other `ddrRead` operations (`191-194`). `pollMotion()` takes the frame-state mutex only after `captureMotion()` returns (`328-339`); frame reads also release the DMA mutex before taking that mutex (`294-313`). No inverse nested lock order was found in these paths. The lock is process-local: a separate observer or other viewer can still corrupt shared driver buffers, which is why positive exclusive-owner checks matter.

RX motion scratch is `0x3FE000`; tag scratch is `0x3FF000`; six image slots use stride `0x97000`, with the sixth frame+16-byte tag ending at exclusive offset `0x38A010`. Both scratch ranges are inside the 4 MiB RX mapping and disjoint from image/tag destinations. CPU frame copy after releasing the DMA mutex is safe against motion reads because motion uses its own scratch. Preserve the whole-snapshot DMA lock, single-word extraction from each 16-byte response, generation checks, and scratch separation when making fixes.

For the requested U2F/scratch concern: the implementation calls its host-to-FPGA operation `H2F_CMD`. Motion selector writes zero the 16-byte TX descriptor payload then copy the low word (`167-172`), under the same DMA lock; this avoids transmitting leftover bytes. RX motion scratch is not used as the TX source. Legacy `regWrite`/`regRead` (`142-151`) do not acquire the mutex and `regWrite` does not clear all 16 bytes; no call sites were found in this candidate beyond the definitions. Do not activate those helpers concurrently without matching lock and payload safeguards.

Polling starts staggered by camera and settles to one poll per second (`377-379`, `328-332`), but one motion transaction can hold the shared DMA lock for about two seconds, plus one in-flight ioctl and lock-queue delay. The two-second budget begins **after** acquiring the mutex and is checked only between ioctls. SIGALRM is process-wide in this multithreaded viewer (`125-139`), so it is not a proven hard interruption of the worker blocked in ioctl; bounded kernel driver behavior remains necessary. Static code comments claim approximately 800 ms driver waits, which this review did not independently verify.

Graceful viewer shutdown stops and joins all six workers (`521-522`), and `Grabber::stop()` waits (`396`). The session helper waits only approximately six seconds plus SSH overhead for the device to become unowned (`55-60`). Queued motion/frame reads can exceed that window under degraded hardware. Use an explicit, justified shutdown deadline based on verified driver timeouts and pending work; on expiry fail closed with PID/owner diagnostics and leave PCIe/module intact. Do not infer that a closed X window means DMA has been released.

## Quiesce/program/recovery boundary

The actual quiesce order is graceful stop → non-forced module unload → PCI remove (lines 63-65), not remove → unload. That order can be reasonable if it matches this driver's established teardown, but verify and record both module absence and BDF absence before declaring success. A second-step failure currently leaves a partially quiesced board without a receipt. Conversely, absent module/remove paths currently count as success without proving the starting state.

`program_100h_motion.py` independently gates completed build/hash/pin/PHY/timing/resource evidence, uses an isolated retained programming directory, checks vendor-process idleness before real execution, validates a single PG2L100H chain, and requires successful SRAM receipt plus parent runtime acceptance for flash. Its `--check` validates/renders without vendor/process/socket access; it is appropriate after PnR completion. It intentionally does not perform viewer/PCIe actions and should keep that separation. Session preflight should consume the parent's validated plan, not bypass these programming gates or invoke them early.

`board_host.py` retains the established override/config/default resolution and lazy SSH connection. No new host-resolution regression was found. `motion_board_session.py` preserves all environment entries actually saved in `viewer_launch_baseline.json`, adds `CAMVIEW_MOTION=1` for the candidate, and retains baseline cwd. It does not replay baseline argv or the complete original process environment; the current saved argv has no meaningful extra argument, and its four saved environment entries match this path. Call this preservation of the **saved** environment, not a guarantee of complete original environment preservation. Validate required DISPLAY/XAUTHORITY and value types before quiesce.

## Suggested parent sequence after fixes

1. Wait for parent PnR/build evidence completion; validate programmer `--check` output and baseline recovery artifacts offline.
2. Preflight receipts, paths, staged candidate hash/mode, saved environment, log destinations, viewer identity/window association, and required host commands while baseline remains live.
3. Acquire the session lock; graceful q; await exact viewer exit and no owners; non-forced unload/remove; save the verified quiesced state.
4. Let the parent run the guarded SRAM programmer, inspect its receipt, then reconnect with exact endpoint/driver/node checks.
5. Launch one hash-verified candidate through an exec-based detached command; validate owned PID, executable, DMA ownership, associated X window, and runtime evidence. Keep the retained baseline restore command ready. Flash remains conditional on the programmer's parent acceptance contract.

No runtime success or hardware readiness is asserted by this static review.
