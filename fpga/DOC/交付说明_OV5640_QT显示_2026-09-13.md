## 1. 系统链路（本次修复后）

```
OV5640(DVP 1280x720 RGB565, ~40fps)
  → FPGA 采集/乒乓写 DDR3 (0x00800000 / 0x00A00000, 每帧1,843,200B)
  → PCIe Gen2 x2 DMA
  → RK3568 camview(Qt5): 轮询 +0x38 帧就绪位 → DMA 读帧 → ACK → QImage(RGB16) → X11 :0 → HDMI
```

### 2.2 根因修复：相机 I2C 时钟域死锁（本次核心 bug）
- **根因**：`ov5640_clk` PLL IP 按 **50MHz** 输入生成（.idf: `CLKIN_FREQ_advancedPage=50.0`），实际 clkin1 接 25MHz free_clk → VCO 落在锁定域外 → **lock 永不置位** → `clk_50m_rst_n = locked & button_rst_n` 恒 0 → I2C 配置 FSM 一笔都没发过（诊断 +0x48 exec_cnt=0 实证）→ 相机从未被配置、从未出流 → 整条链路无图。
- **修复**（[CLKFIX] 标注）：`clk_50m` 直接由 free_clk(25MHz) 驱动（PLL 旁路）；`CLK_FREQ` 参数 50M→25M（SCCB 仍为 250kHz）；`clk_50m_rst_n` 改为 `1'b1`。
- **连带修复**（[RSTFIX]）：`button_rst_n`(M15) 板上悬空读 0 且无上拉，已解耦出相机复位并在 pcie.fdc 加 PULLUP。
- PLL 分频比试验修改（M/F→48）后仍不锁定，最终采用旁路方案；IP 的 `.idf` 若日后重新生成，请务必把输入频率改为 25MHz。

## 4. 运维要点（重要）
1. **每次 JTAG 烧录后必须**：`rmmod → remove → rescan → insmod`，否则总线主控 DMA 全部静默死锁（已复现两次并记录恢复流程）。
2. **串口大量连续传输 >~115s 会触发 RK FIQ 调试器截获控制台**（串口 BREAK；与数据内容无关）。恢复：发 `console\r\n`。传输工具已改为 hex 分片+断点续传（xfer_hex.py / pull2.py）。
3. 串口数据里出现字面量 `fiq` 三个字符会立即触发 FIQ 调试器（这是选用 HEX 编码的原因）。
4. 相机写引擎流控：两帧未 ACK 即自动停写（设计行为）；camview 读帧后即 ACK，无需干预。
5. `project_build/` 是 09-12 晚的过时并行编译副本，可删。
6. 仿真回归 tb_ovreg_axil_decode 失败为既有问题（寄存器窗连续读数据混叠），与本批改动无关；camview 的读帧走 DMA 大块读，不受影响。

## 8. 追加（09-13 上午）：画面冻结根因与自动恢复

**现象**：显示跑通后，过一段时间画面冻结在两帧来回切换、不再跟随摄像头。

**根因链**（dmesg 铁证）：
1. camview 每帧一次 ACK 写(M01) + 周期性寄存器读，持续数小时的高频 M01 事务；
2. FPGA 的 **PCIe DMA 完成通路（MSI）楔死**：dmesg 出现 `PCI_DMA_READ/WRITE Error: Timeout waiting for MSI interrupt`，此后所有读写永久超时；
3. camview 的轮询/ACK 卡死 → 引擎两帧未 ACK 停写（设计流控）→ 显示冻结在 A1/A2 两帧来回切。
4. 加速因素：多个 camview/守护实例并发抢驱动（已加 /tmp/camview.lock 单实例锁 + 清理流程）。

**恢复流程**（全自动）：PC 端运行 recover_display.py 看门狗——每 60s 读窗口标题 fps，冻结 2 次即自动：JTAG 重烧 → remove/rescan → insmod → 重启 camview（全程约 1 分钟）。

**根治方向**（下一工作项）：M01 通路 RTL 排查——寄存器窗 b2b 读 bug（读返回上一次数据，同 tb_ovreg_axil_decode 仿真失败）+ axi_to_axi_lite/写通道在持续负载下的楔死点。该 bug 同时污染所有诊断寄存器读数（读数=上一次的值），修复后诊断体系才完全可信。

## 9. 最终修复（09-13 11:33 比特流）：MSI 风暴根除

**冻结的直接根因**：自由运行模式下 xdma_req 恒为 2'b11 → 相机 MSI 中断线持续为高 → PCIe 核心被 MSI 风暴持续轰击 → 主机所有 DMA 操作超时（dmesg: PCI_DMA_WRITE/READ Error 雪崩）→ camview ACK/读全部卡死。

**修复**：top.v 相机 MSI 源关断（[MSIFIX]，msi_req 中 cam_irq 位改常数 0）——自由运行模式下相机 MSI 无用途（无 ACK 流控、无中断同步需求）。

**验证**（11:40 烧写后连续运行）：fps 稳定 17.0；10 分钟内仅 1 次 DMA 超时（0.01% 错误率）且 camview 自动恢复；对比修复前同期的持续超时雪崩。

**当前运行架构**：
- 引擎自由运行，不断交替覆写 A1/A2（无 ACK 流控、永不停写）
- camview 固定节拍(25ms+DMA)轮流读 A1/A2 → 显示（无任何 M01 寄存器访问）
- 已知代价：读写碰撞造成的偶发撕裂帧（约 1/4 读次，暗场下不可见）；如需消除，下一版可在 RTL 加硬件帧序号寄存器供主机做新鲜度判断
