## 0. 结论速览

| 项 | 内容 |
|---|---|
| 撕裂根治 | FPGA 相机写引擎每帧写完追加一笔 16B 写: 32bit 帧计数器落在 DDR `帧基址+0x96000`；主机只读"序号最大"的缓冲 → 读写永不撞同一块缓冲，撕裂结构性归零 |
| 检测画框 | RK3568 NPU 跑 YOLO26n(.rknn)，detview(Qt5) 实时画框，模型热键切换 |
| 颜色格式 | 传输保持 RGB565(传感器只有 5/6/5 bit，传输 RGB888 零增益白多 50% 带宽)；模型输入在主机侧转 RGB888(位复制) |
| 版本匹配 | 模型是 rknn-toolkit2 2.3.2 转换 → 板上必须用 librknnrt.so **2.3.2**(包内已带)；板端 RKNPU 内核驱动 v0.9.8 已验证存在 |

## 1. 系统链路

```
OV5640(DVP 640x480 RGB565 ~28.6fps)
  → ov5640_ddr_w(打包 128bit) → axi_dma_write(S01) → DDR3 帧缓冲 A/B
      ↘ [FRTAG] 每帧完成后 16B 写帧计数器 @ 帧基址+0x96000
  → RK3568 detview:
      采集线程: 轮询两个序号槽 → 读序号最大者的整帧 → ACK
      推理线程: RGB565→RGB888 → letterbox(上下各补80行) → rknn_run → decode(e2e/std) → NMS(std)
      UI线程: QPainter 画框+HUD → QLabel
```

## 2. FPGA 改动([FRTAG 2026-09-14] 标注)

| 文件 | 改动 |
|---|---|
| `source/ov5640/ov5640_ddr/ov5640_ddr_w_ctrl.v` | FSM 增加 ADDR_TAG/DATA_TAG 两态: 帧尾追加第二条 16B 命令(地址=帧基址+CAM_DATA_LEN×16, 数据=32bit 帧计数器); vsync 上升沿改粘滞锁存(vsync_pending, 防 tag 期间丢帧头); 1M 周期看门狗, tag 卡死立即回 IDLE, **主帧通路永不阻塞** |
| `source/ov5640/ov5640_ddr/ov5640_ddr.v` | 数据流加 mux: DATA_TAG 期间用计数器拍替换(空闲的)相机流; 相机流短暂 stall 由 FIFO 吸收 |

设计要点:
- axi_dma_write 是**纯长度驱动**(cmd_len 决定搬运量, top.v 里 data_in_last 未连), 背靠背两条命令原生支持。
- 帧基址在帧命令接受时刻锁存(w_ping 翻转前), tag 地址 = 该帧缓冲基址 + 帧字节数。
- tag 拍 last=0, 不污染 cam_s_data_last 语义(仍每帧一拍)。
- 地址布局零冲突: A帧 0x00800000..0x00895FFF, tag@0x00896000; B帧 0x00A00000.., tag@0x00A96000。缓冲间距须 ≥ 帧大小+16B(默认 2MB 间距满足)。
- 仿真: `sim/ov5640_tb/tb_ov5640_ddr_w_tag.v` — 4 帧全检(命令序/地址/长度/tag值=帧号/xdma_req) PASS。

## 3. 主机侧取帧规则(detview)

- 每 ~4ms 轮询两个 16B 序号槽(纯 M00 数据通道, 全程不读 M01 寄存器窗)。
- `argmax(计数器)` 的缓冲 = 最新完整帧; 正在写的缓冲计数器恒为次大 → 数学上不撕裂。
- 旧比特流(序号恒 0)自动退回 `STBL-FALLBACK`: 整帧双读比对, 相同才显示。
- 读后照常写 ACK(兼容 ACK 流控比特流, 自由运行忽略)。

## 4. RGB565 vs RGB888 结论

- **传输保持 RGB565**: OV5640 DVP 8bit 总线只能出 565(0x4300=0x61), 888 的高位全是复制位, 改传输=白多 50% 带宽+改 RTL。
- **模型输入 RGB888**: detview 在主机侧位复制转换 `r8=(r5<<3)|(r5>>2), g8=(g6<<2)|(g6>>4), b8=(b5<<3)|(b5>>2)`, 显示与推理共用同一转换(B/C 热键同时作用于两者, 保证显示和检测看到同一张图)。
- 若量化掉点明显: 用 565 转换后的图重新跑 rknn-toolkit2 量化校准即可。

### 7.2 事故记录: rmmod -f 楔死板上控制台

- **经过**: PCIe 恢复仪式中使用了 `rmmod -f`(强制卸载)。FPGA 刚被重新烧录, 驱动的 DMA 状态机与新比特流错位, 强制卸载触发内核级死锁: shell 卡死(D 状态), 内核本身存活(RTW 心跳持续), 但串口输入无回显、FIQ 调试器(BREAK)亦无响应。
- **教训(新运维铁律)**: 重载驱动**只用普通 `rmmod`**; `rmmod -f` 对带未完成 DMA 事务的 PCI 驱动 = 控制台死刑。若普通 rmmod 失败, 先检查是否还有进程占用, 然后走断电重启。
- **影响**: 板端需人工断电重启(无远程电源控制)。重启后 FPGA 从 SPI Flash 加载旧比特流(该 flash 为 eON 0x1C7118, 不在 PDS 支持表, 无法固化新比特流, 已验证失败并放弃), 故 auto_recover.py 在控制台恢复后**先经 JTAG 重烧再继续**。
- **自动恢复**: `auto_recover.py`(工作目录)看门狗每 30s 探测 COM9, 控制台恢复即自动执行: JTAG 重烧 → PCIe 仪式(普通 rmmod) → 帧序号递增验证(TAG-SYNC 判据: 25 次轮询计数器增量 ≥5) → 推送 lib+模型(base64+流水线加速) → 板上 qmake+make → `--selftest 12` → 启动 GUI → e2e/std 对比。全程写 auto_recover.log, 跑到 09:00。

### 7.4 夜间自主执行手册(auto_recover.py)

### 7.7 模型分类分支零输出问题(未解决, 需训练侧介入)

**现象**: 完美输入下(RGB/letterbox/尺寸全部核对无误, 模型输入缓冲已 dump 回传目检), 4 个模型的
box 坐标分支输出结构正常(8400×4 坐标呈规律网格), 但**分类得分通道在原始 INT8 层面精确等于
zero_point(-128)**, 即反量化后全零 → 永远无框。

**已排除**: 解码代码(两种布局假设都试过)、输入格式(uint8/手工量化 pass_through 各试过)、
反量化参数(zp/scale 直接从 attr 读取)、e2e vs std(同样症状)。

**最可能根因**: 模型 README 自己警告的 `Unkown op target: 0`(std 7 处 / e2e 15 处)——分类路径
的算子(最终 sigmoid/classify 段)回退 CPU 后在真机上输出全零。转换时 PC 仿真一致性 0.9999997
不能代表真机行为(RK3568 NPU 0.8TOPS + runtime 2.3.2 + 驱动 0.9.8 组合)。

**修复方向(需训练环境, 本机无)**:
1. 用 rknn-toolkit2(建议 2.3.2 同版)重新转换, 转换日志中**不允许出现 Unkown op target**;
2. 或在 export 时保留 NPU 支持的算子组合(YOLO26 e2e 头的 TopK/GatherElements 是重灾区,
   可先转 std 头模型验证分类通道);
3. 或降到 toolkit 2.3.0/2.2 重转(与板上驱动 0.9.8 世代更匹配)后真机复测;
4. 每次重转后用本工程 `--image` 模式 5 分钟即可完成真机验证:
   `QT_QPA_PLATFORM=offscreen ./detview --image test_car.ppm --model 0`
   (test_car.ppm 为日间街景车辆图, 已在板上 /root/ov5640/)

### 7.9 【根因更新 2026-09-14 上午】不是模型问题, 是板端 NPU 算子执行问题

在 WSL(Ubuntu-24.04) 里装好 rknn-toolkit2 2.3.2, 用本机 ultralytics 8.4.121 从 yolo26n.pt 导出
ONNX(e2e 头 [1,300,6]), 用**同一套转换流程**做了对照实验:

| 实验 | 结果 |
|---|---|
| 对照模型 PC 仿真(rknn-toolkit2 simulator) | ✅ **正常**: 得分 0.321/0.288, 检出 2 框(x1=546 y1=171 x2=640 y2=242 cls=2) |
| 对照模型 板端 RK3568 实机 | ❌ **垃圾**: 坐标槽全部饱和到 int8 最大值(650.6 = (127-(-126))×2.57155), score 槽精确=zero_point |
| 用户 zebra/vehicles 模型 板端 | ❌ 同样症状 |

**判定: 转换流程本身正确(仿真为准), 问题在设备端执行。** 机理: 转换日志的
`Unkown op target: 0`(来自 YOLO26 检测头的 TopK/GatherElements/Where/Concat/Reshape 段)意味着
这些算子**没有有效设备目标**; 仿真器走 onnxruntime 所以结果正确, 而 RK3568 NPU 上这些算子
产出垃圾/饱和值 → 检测头输出不可用。这是 **rknn-toolkit2 2.3.2 对 YOLO26 e2e 头的支持缺陷**,
与用户模型、我的转换脚本、detview 解码代码都无关。

**诊断证据(可复现)**:
- 模型输入缓冲 dump 回传目检: 图像/letterbox/RGB 全部正确 (model_input.ppm)
- 原始 INT8 输出 dump: box 分支结构正常/分类分支精确=zp
- 对照模型同样流程: 仿真对/设备错 → 排除"我方代码"与"用户模型"
- 板端 NPU 健康: /sys/kernel/debug/rknpu/version=v0.9.8, freq=900MHz, load 正常

**可行修复路径(按优先级)**:
1. **换 std 头模型 + 避开不受支持算子**: 导出时去掉 e2e 的 NMS/TopK 段(只保留 conv+sigmoid 原始头),
   detview 已内置 std 解码路径([1,4+nc,8400] + 自写 NMS)。**注意**: 用户现有 std 模型
   (README 记录 7 处 Unkown op) 也需重转, 目标是把 Unkown op 降到 0。
2. **升级 rknn 工具链/runtime**: 试 rknn-toolkit2 2.x 更新小版本或 rknn_model_zoo 的 YOLO26 官方转换
   方案(其已适配 RK 平台算子); 本机取证时 master 分支 runtime 与 2.3.2 同 hash, 故需等新发布。
3. **fp16 转换**: 若量化是饱和主因, fp16(不量化)可能绕过 → 正在板端验证 (yolo26n_ctrl_fp16.rknn)。
4. **回退到 YOLOv8/v11 头**: 该头在 RK3568 上生态成熟(rknn_model_zoo 全套 + 训练/量化脚本),
   代价是重训模型。

**给训练侧的明确交付要求**: 重转后**转换日志中 `Unkown op target` 必须为 0**; 验证用 5 分钟真机回归:
