# detview 性能优化计划与 TODO

## 目标与当前状态

目标是在六路监看、选中路识别及模板追踪同时工作时，减少 detview 相对新版 camview 的显示损失，保持帧所有权、检测有效期、来源切换和暂停恢复正确。

本文件同时记录执行状态；勾选须附验证依据。当前已开始推进刷新修正、显示统计，以及C1/C2、C5/C6双目和模板匹配的软件任务。执行过程见[task_plan](task_plan.md)、[findings](findings.md)和[progress](progress.md)。

- [x] 核对新版 camview 显示源码、实际启动配置与 detview 最新源码。
- [x] 留存原始帧直传、独立纹理及局部 HUD 更新后的构建、自测、实板日志与截图。
- [x] 确认重复清空空车道掩码会使 HUD 缓存失效。
- [x] 形成分阶段计划、测试矩阵和验收条件。

## 优先级与执行顺序

## 阶段1：修正无效刷新，建立分段计时

涉及 `main.cpp` 的设置函数、100ms过期定时器、`paintGL()`、`uploadOverlay()` 与显示统计。

- [x] **1.1 空掩码重复清理只发生一次。** `setLaneMask({})` 在当前已为空时直接返回；有掩码时仍按TTL清除一次。重复空值不增加检测版本号、不请求重绘。
- [x] **1.2 将检测内容变化与过期检查分开。** 相同检测几何、文字、来源和有效期不重复使HUD失效；分数、追踪状态、深度或有效期变化仍正确更新。不用无条件延长TTL换取缓存命中。
- [x] **1.3 定时器按必要事件刷新。** 将检测过期、指标更新和全窗 `update()` 区分；无变化时保留缓存。暂停后统计归零、旧框清除通过实板截图；距离过期通过离线回归，实物仍待标定。
- [x] **1.4 增加分段墙钟计时。** 分别统计相机纹理上传、HUD区域计算、CPU栅格绘制、区域打包、HUD上传、相机绘制和HUD绘制。统一明确起止边界；不要把CPU调用时间命名为GPU耗时。
- [x] **1.5 增加工作量计数。** 记录HUD失效原因、重建次数、上传矩形数/字节数、绘制矩形数、文字缓存命中/未命中/清空次数，以及相机每路上传次数/字节数。
- [ ] **1.6 记录帧交接延迟。** 记录采集完成、快照发布、GUI消费、纹理上传和绘制提交时间；记录被最新帧替换的数量。所有时间用同一单调时钟。交换完成单独计数，不将其解释为屏幕扫描完成。
- [x] **1.7 增加低开销统计出口。** 在固定窗口汇总计数、平均值及有界分布的p50/p95/p99；避免逐帧打印、无界样本和同步写盘。可关闭详细测量以核对计时本身的损失。

验收：静止且没有检测/车道内容时，HUD不会被100ms空清理反复重建；正常指标刷新仍保留。分段计时与总回调耗时近似一致，未覆盖部分单独记录。窗口总事件数除以窗口实际时长得到吞吐，不再用每5秒抽取的一秒窗口代替全程平均。

## 阶段2：建立可比较的基线

涉及 `scripts/validate_detview_direct.py`、`scripts/analyze_detview_direct.py`，必要时加入明确标记的性能诊断参数。

- [ ] **2.1 测试前协调设备独占。** 记录原运行程序、启动参数、相关Qt/显示环境及设备占用；在已协调的测试窗口顺序运行，结束后恢复原程序。遇到另一个agent重新占用设备时停止依赖设备的测试并保留记录。
- [ ] **2.2 固定比较条件。** 同一分辨率、窗口尺寸、RGB565协议、模型、阈值、相机模式、提交间隔、显示同步、纹理槽数和OpenCV线程数。记录温度与频率；不默认锁频。
- [ ] **2.3 区分静止场景与运动场景。** 静止场景固定目标数量和框尺度；运动场景使用可重复动作。先用可重复的离线帧序列验证计算开销，再用真实六路验证整体吞吐，分别报告。
- [ ] **2.4 扩充测试矩阵。** 采用下表，先短测筛选，再对基线与最终候选各重复3次。
- [ ] **2.5 每次保留10秒预热及60秒独立采样窗口。** 性能窗口内关闭自动截图；UI截图在窗口结束后单独进行。对比过程中场景变化或被其他进程打断，标记该轮无效。
- [ ] **2.6 对齐帧率口径。** 两版都记录实际相机上传、含新相机内容的绘制、总绘制和交换计数。detview额外保留快照发布/消费、NPU请求/开始/完成/失败。
- [ ] **2.7 汇总全窗口而非抽样窗口。** 输出总计数/实际时长、帧间隔分位数、GUI延迟、分段耗时、CPU核数、RSS、负载和错误；一秒窗用于展示波动。

| 组别 | 目的 | 控制变量 |
| --- | --- | --- |
| A. camview六路 | 同期纯显示参照 | 相同窗口、同步、纹理槽数和场景 |
| B. detview六路，仅显示 | 单独测显示架构损失 | 显式诊断模式关闭分析工作，不加载识别结果冒充正常运行 |
| C. B + 固定检测频率 | 测RGB转换、NPU与结果交接开销 | 固定为同一检测间隔，如250ms |
| D. C + 模板追踪 | 单独测追踪增量 | 保持检测间隔、目标数、框尺度一致 |
| E. 正常自适应识别追踪 | 测真实产品行为 | 使用正常弱匹配提前检测规则，单独报告实际请求率 |
| F. 单路显示 | 区分六路资源压力 | 与六路选中同一相机，分析参数一致 |

直接使用当前 `--no-tracking` 会进入更频繁的NPU调度，不能代替C/D对照。若需要固定频率诊断选项，应单独实现并在日志中标明，保留正常默认调度行为。

验收：能分别回答“纯显示差多少”“检测增加多少”“追踪增加多少”；若场景无法固定，不把结果归因于单个代码改动。

## 阶段3：减少 HUD 上传与绘制负担

仅在阶段2确认HUD是主要热点后执行；涉及 `paintGL()`、`uploadOverlay()`、文字缓存和区域绘制。

- [ ] **3.1 将慢变文字与动态框分开更新。** 指标和工具栏保持合理刷新周期；目标几何随最新有效结果更新。深度、检测TTL过期仍单独触发清理。
- [ ] **3.2 目标标签按实际图像尺寸计算区域。** 去掉“从框左边一直到相机右边”的宽区域；正确覆盖字体DPI、背景、边缘裁剪和长标签。
- [ ] **3.3 合并碎片区域。** 根据矩形数量和增加的像素面积，比较逐矩形、有限合并及单块更新；避免以减少字节数为代价制造大量GL调用。重叠区域只混合一次。
- [ ] **3.4 复用区域打包缓冲。** 用可复用的连续缓冲代替每个矩形一次 `image.copy()` 分配；GLES2行步长仍必须正确处理，不能直接假定整窗区域连续。
- [ ] **3.5 改进文字缓存淘汰。** 替换达到约65条后全部清空的策略；设置内存上限并按使用情况淘汰。必要时将显示数值格式稳定化，但不能减少真实检测状态更新。
- [ ] **3.6 保留新旧区域清理。** 框移动、消失、切相机、切来源、设置返回和窗口变更时，旧纹理像素不会重新显现。

验收：HUD上传字节/调用数、CPU栅格及打包耗时明显下降，并带来可重复的总显示收益；没有文字裁切、重复alpha混合、框残影或过期距离。只降低HUD指标刷新率但不改善总吞吐的改动，不算达到本阶段性能目标。

## 阶段4：优化 GUI 交接与显示调度

涉及 `VisionPipeline::tracksReady`、控制器信号回调、结果邮箱和Qt显示配置。

- [ ] **4.1 计数分析结果排队。** 测量追踪发布次数、GUI处理次数、队列延迟及被更新结果替换次数，确认分析结果是否拖慢相机消费。
- [ ] **4.2 必要时增加按模型的最新结果邮箱。** 相机帧邮箱已有限界，不重复实现；追踪显示结果按来源代号、模型和帧号合并，单次通知消费最新结果。推理反馈与历史纠偏仍完整送达计算线程，不能用显示合并丢弃分析反馈。
- [ ] **4.3 移出GUI里的推理输入准备。** 评估将640×640补边、分配和像素复制放到推理线程；保留原始帧所有权、来源代号与帧号，不增加额外中间复制。
- [ ] **4.4 分别对照Qt更新等待与显示同步。** 核对实际环境，独立测 `QT_QPA_UPDATE_IDLE_TIME`、swap interval，不同时改变多个参数；保持及时键盘响应。
- [ ] **4.5 按吞吐调整显示提交节流。** 比较不同提交间隔下的GUI通知、消费延迟和新画面吞吐；不让“提交60次/秒”成为目标，不牺牲画面新鲜度来抬高统计。

验收：相机GUI消费和绘制延迟降低；分析显示队列有界；旧来源、旧模型结果不能覆盖新画面。暂停、切相机、设置页返回均正确。

## 阶段5：降低追踪、预处理与回放成本

涉及 `vision_pipeline.cpp`、`template_tracker.cpp` 和相机分析帧生成。

- [ ] **5.1 补齐分析线程分段计时。** 单独测RGB565转RGB888、灰度转换、缩放、模板匹配、快照复制、检测纠偏和历史回放；当前追踪计时未覆盖灰度转换，不能当作整个分析成本。
- [ ] **5.2 限制匹配模板的工作尺寸。** 根据目标大小选择计算分辨率或限制模板最大尺寸；坐标仍映射到原始640×480，不能靠缩小显示框省算力。重点验证大框、近景目标和纹理变化。
- [ ] **5.3 有界处理追踪帧。** 对过快输入优先处理最新帧，测15/20/30Hz等候选频率；使用实际时间间隔进行预测，检测TTL仍从原始检测时间计算。快运动精度与延迟一起验收。
- [ ] **5.4 减少重复灰度/缩放。** 在模型之间及历史回放中复用只读预处理结果；若引入共享图像，保持快照隔离，不允许后续模板适配修改历史像素。
- [ ] **5.5 减少快照深拷贝。** 先测快照占比，再选择只读共享或更紧凑快照；检测纠偏和回放仍产生独立可写状态，保证与原始逻辑结果一致。
- [ ] **5.6 记录检测请求拒绝原因。** 区分间隔限制、待完成请求、存在更新输入帧、重复帧及配置切换；同时测GUI请求/结果往返延迟。确认是否因持续新帧使请求饥饿，再调整策略。
- [ ] **5.7 对照OpenCV线程数。** 固定场景比较1/2线程对追踪耗时、GUI尾延迟及CPU的影响；线程数多不默认代表整体更快。

验收：在相同检测频率和目标条件下，追踪增量CPU、p95分析耗时及GUI影响下降；已有追踪自测通过。对尺寸限制、调度或快照改动补充有实际意义的回归验证：大框、遮挡、快运动、历史纠偏、来源重置和有效期。不能仅以减少NPU调用为成功标准。

## 双目测距任务：C1/C2、C5/C6

- [x] **S1 双组配置和兼容CLI。** 为C1/C2、C5/C6提供独立配置，每组左右相机、640×480标定、同步确认、tag偏移及计算间隔独立；保留旧单组CLI。不跨组或复用别组标定。
- [x] **S2 独立引擎与帧配对。** 两组拥有独立校正/匹配器、帧水位、过期状态与深度缓存；采集仍共用一PCIe实例和已有原始帧。支持标签回绕、无新帧、异步和切来源重置。
- [x] **S3 有界计算与性能统计。** 两组有界保存最近帧，按组记录配对成功/失败、计算耗时和深度年龄；低分辨率和间歇计算，避免两组SGBM持续抢占追踪与显示。
- [x] **S4 目标深度映射和UI。** 选中C1或C5时用对应左图同帧目标ROI；选中右图先不宣称左图深度可直接移用。离线融合/过期回归、实板两组预览与设置状态通过；真实目标深度仍待标定验收。
- [x] **S5 双组离线回归。** 合成/固定输入验证各组独立深度、互不污染、切来源重置、缺帧与标签偏移；未标定/未确认同步不输出可信米数。
- [ ] **S6 独立标定与同步核实。** 分别获取C1/C2、C5/C6的K/D/R/T及基线，确认曝光同步与共同帧号语义，核实左右顺序。等待用户提供硬件参数，软件完成不代表此项完成。
- [ ] **S7 实物距离和性能验收。** 用户指定测试时机后，两组分别测已知距离、不同ROI、遮挡/运动、有效深度比例、误差与延迟；同步记录六路显示/CPU/NPU损失，不用中心深度代替目标深度。

## 性能目标与停止条件

1. **必须满足的门槛：** 功能与帧所有权正确，来源切换和TTL可靠；受控测试无新增采集、GL及内核错误；所有计数口径可比较。
2. **阶段性目标：** 对照测试中将六路正常识别追踪的新画面吞吐推进到30fps以上，降低GUI尾延迟；这是工程目标，尚未验证可达，不用降低识别/追踪质量换取数字。
3. **接近camview的目标：** 同场景、同配置、同口径下，正常detview显示吞吐达到camview的80%以上。若同期camview约39fps，对应约31–32fps；按实测参照计算，不固定使用历史39fps。
4. **纯显示诊断目标：** detview只显示时尽量接近camview，建议差距不超过10%。若纯显示已接近而正常模式仍落后，转向分析线程和CPU竞争，不继续盲改shader。
5. **资源与延迟要求：** 不出现持续RSS增长，CPU和温度的增量有解释；平均帧率提高但p95/p99画面间隔或GUI延迟恶化时，不直接接受候选。
6. **停止条件：** 分段计时与重复对照表明剩余损失来自必要分析工作，且进一步改善需要改变精度、硬件协议或产品行为时，记录证据、收益与代价，形成下一项决策，不无限叠加优化候选。
